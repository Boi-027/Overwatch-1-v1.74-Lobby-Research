################################################################################
##  READ THIS FIRST - MAJOR CORRECTION (2026-08-25)
################################################################################

A large block of prior reverse-engineering work was based on a
MISIDENTIFICATION. If you have an older copy of this document, discard its
"accept mechanism" section entirely.

WHAT WENT WRONG
---------------
On 2026-08-11, two handler functions were identified by decrypting the
client's log-format strings and matching them to a names table:

    0x86BEE0  -> "ResponseConnect"
    0x86F432  -> "ResponseLogin"     (also seen as 0x86C320 in older notes)
    0x261AB68 -> names table

These were assumed to be the LOBBY protocol's connect/login handlers.

They are not. They belong to the VOICE CHAT client.

HOW IT WAS CAUGHT
-----------------
The names table at 0x261AB68 was examined in IDA. Its full contents:

    ResponseConnect, ResponseLogin, LoggedOut, LoggedIn, LoggingIn,
    LoggingOut, Resetting, ResponseLogout, ResponseDisconnect,
    ResponseJoinChannel, ResponseStartTransmit, ResponseLeaveChannel,
    Disconnected, Connected, Ringing, Connecting, Disconnecting,
    ChannelConnection, SetOutputVolume, SetInputVolume

JoinChannel / StartTransmit / LeaveChannel / SetInputVolume /
SetOutputVolume / Ringing are voice chat concepts. This is the VC client's
message table.

Corroborating evidence, in the game's own log file (--tank_logpath):

    [NRM] [VoiceChat] ... #=[VC] ResponseGetOutputDevices 01 0(0:811c9dc5) (...)
    [NRM] [VoiceChat] ... #=[VC] ResponseSetActiveOutputDevice 02 0(0:811c9dc5)

That output format - name, 2-digit number, 0(0:<fnv>), parenthesized string
fields - is EXACTLY what 0x86BEE0 constructs. 0x811C9DC5 is FNV-1a of the
empty string, the same constant the function seeds its two string loops with.
The channel tag on every such line is [VoiceChat].

WHY IT FOOLED ME FOR THREE WEEKS 😭
--------------------------------------
- The handler dispatch table is PER-CONNECTION (conn+0x250). msgid 0x101 maps
  to completely different handlers on different connection types. Finding a
  handler at slot 0x101 never implied it was the lobby's.
- The msgid gate is "<= 0x4F0", so 0x100/0x101 are plausible ids in many
  tables. The numbers matching meant nothing.
- The identification came from strings tagged [VC], which was visible in the
  evidence from day one and not questioned.
- Every symptom was consistent with "we haven't cracked it yet" rather than
  "we're looking at the wrong subsystem": the pending map read empty during a
  lobby park (because VoiceChat was not connecting), no high-entropy token
  ever appeared (because no VC connect was pending), and the lobby client
  closed the socket no matter what was echoed (because nothing was answering
  what the lobby actually wanted).

LESSON FOR WHOEVER PICKS THIS UP
--------------------------------
Before investing in a handler, confirm which SUBSYSTEM's table it belongs to.
Dump the whole names table, not just the entry you were looking for. If the
neighbours are about audio devices, you are in the wrong place.


################################################################################
##  SECTION 1: WHAT IS SOLVED AND VERIFIED (lobby-side, still good)
################################################################################

Everything in this section was validated independently of the VoiceChat
mistake and remains correct.

[SOLVED] JAM cipher - reimplemented server-side in lobbyserv.py (Jam class).
  Known-answer test (independently confirmed by a second implementer):
    key    = 00 01 02 ... 1f  (bytes 0x00 through 0x1F)
    first 64 bytes of keystream:
      f07e5df1c8d51c0d754da6ddde34cca01db0ed26334eb94ae277135a0764c6a6
      794d7ab0cc0978ef43de30766a7ee1d7c90e159df239d4016d450fa3d8207842
  If your implementation reproduces this, your cipher is correct.

[SOLVED] 292-byte state blob.
  BLOB_KEY (64 bytes):
    35 86 F3 62 8A 63 1B 70 57 12 40 5B 8A CC 71 D4
    0F D1 67 0C C1 B0 3E A3 84 97 4A 6F B1 A7 61 96
    B1 42 F0 B7 23 10 EA 81 16 D0 0A 4C 35 2F 09 AC
    DB FB 50 A6 3E C5 15 3E 62 E4 D6 7F E0 9B EE CC
  Construction:
    256-byte body, body[i] = i & 0xFF
    body[0]        = 0x02
    body[1:5]      = 7F 00 00 01        (127.0.0.1)
    body[255]      = 0xFF               (forces blob >= n, RSA path skipped)
    body[176:208]  = HMAC-SHA256(BLOB_KEY, body[0:176] + body[208:256])
    + 36 trailing zero bytes            => 292 bytes total

[SOLVED] Handshake to state 6.
    C->S  "HELLO PRO CLIENT\0"                  (17 bytes)
    S->C  "HELLO PRO SERVER\0"                  (17 bytes)
    C->S  [8 bytes padding][32-byte cn]         (40 bytes)
    S->C  [32-byte srv_rand][1 byte difficulty][32-byte sn]
          (lobbyserv sends difficulty=0; real servers send 0x07 and 0x09 in
           the two captures examined. 0 = no proof-of-work required, which
           the client accepts.)
    C->S  [8 bytes padding][32-byte MAC1]       (40 bytes)
          MAC1 = HMAC-SHA256(ZERO_KEY, cn || sn)
    S->C  MAC2 || JAM(blob)
          MAC2 = HMAC-SHA256(ZERO_KEY, sn || cn)
  Keys:
    rx (server->client) = HMAC-SHA256(ZERO_KEY, cn || sn)
    tx (client->server) = HMAC-SHA256(ZERO_KEY, sn || cn)
  ZERO_KEY = 32 zero bytes.

  CRITICAL: MAC2 and the blob are ONE CONTINUOUS cipher stream. Do not
  reinitialize JAM between them. If you send them as separate socket writes,
  the leftover keystream from the partial block must carry over. Encrypt all
  292 blob bytes in the same stream, offset 0, no header. Getting this wrong
  produces a client that decrypts the blob, counts all 292 bytes, and then
  silently closes - a very confusing failure mode.

[SOLVED] Counter gate on the first reply.
  The connection counter at conn+0x88 initializes to 1, and a reply's parsed
  index field must be BELOW it. So the FIRST server reply must carry
  counter = 0. Encoding 01 00 00 00 is the value 1, not 0 - this exact
  off-by-one silently killed every reply for weeks.

[SOLVED] Wire frame format - CORRECTED from real traffic (see Section 2C).
  Outer framing: [u24be frame_len][u16be msgid][ ... ]
  The third field is MSGID-DEPENDENT. For some ids it is a u32le payload
  length (verified 96/96 on retail msgid 0x4401); for others it is a counter.
  Frames may also be BARE - msgid only, two bytes, no payload at all. The
  real server's first reply to its client's opening message is exactly that.

  What lobbyserv sent for months instead:
    [u16be msgid][u32le counter][u32le family = 0x11D82194]
    [u16be bnet-hdr-len][protobuf Header{...}][protobuf body]
  The family id and bnet envelope were assumptions, never confirmed against
  a real server. See Section 2D.

[SOLVED] Injection chain that survives Arxan.
  bink2w64.dll (proxy) -> loads bink2w64_original.dll + your DLLs.
  Rename the real bink2w64.dll to bink2w64_original.dll and drop the proxy in
  its place under <GAME>\Overwatch\_retail_\.
  ALL ~75 Bink exports must be forwarded via
    #pragma comment(linker, "/export:NAME=bink2w64_original.NAME")
  A single missing export produces a "Failed to load" dialog before any of
  your code runs. Verify with: dumpbin /exports bink2w64.dll

[SOLVED] Arxan constraints - what works and what does not.
  - VirtualProtect on Overwatch.exe's own .text: BLOCKED EVERYWHERE.
    Measured: 11,408 of 11,408 executable pages denied, all err=87.
    This is blanket, not regional. Inline code hooking (MinHook trampolines)
    is impossible inside the game module. MH_EnableHook returns error 10
    (MH_ERROR_MEMORY_PROTECT).
  - Inline hooking of EXTERNAL modules (winmm.dll etc.) WORKS fine. Verified
    with a MinHook probe on timeGetTime: hook installed, process survived.
  - Heap writes (WriteProcessMemory / direct writes to heap objects) work with
    no Arxan reaction.
  - SuspendThread trips the Arxan watchdog - the client dies at arming.
  - PAGE_GUARD on image (SEC_IMAGE) pages: unsupported, VirtualProtect err=87.
  - x64dbg + ScyllaHide (all presets): defeated. No live debugger, no
    breakpoints.
  - Surviving toolset: plain ReadProcessMemory from an external tool, plus an
    in-process injected DLL doing reads and heap writes only.

[SOLVED] pe-sieve dump characteristics.
  Dumping the live process yields DECRYPTED .text (code is reliable, and this
  is what you load in IDA). However .rdata (vtables, message schema, string
  tables) is ENCRYPTED and shifted by roughly 0x10000. Treat every data-section
  address from the dump as untrustworthy; read data live instead.
  Consequence in IDA: indirect calls through vtables cannot be followed
  statically, and xrefs that pass through .rdata do not resolve.

##  SECTION 2: LOBBY-SIDE FACTS (still believed correct)
################################################################################

LAUNCH (tournament mode - bypasses bnet login, dials the lobby directly)
    cd /d "<GAME>\Overwatch\_retail_"
    Overwatch.exe --tank_TournamentMode --lobbyServer=127.0.0.1:3724 --console --tank_logpath "<LOGS>"

  START -> ENTER GAME dials 127.0.0.1:3724. No bnet contact in this mode.
  Note: tournament mode locks alt-tab; use Ctrl+Alt+Del to escape.

OBSERVED TRAFFIC (this is lobby-side and trustworthy)
  After state 6 the client sends, JAM-encrypted:
      0100 01000000 9421d811     (10 bytes)  msgid 0x100, counter, family
      0103                       (2 bytes)   retransmit/poll
  Then it cleanly closes if unsatisfied. It sends the SAME bytes every
  connection - there is no visible per-connect nonce on the wire.

  A TYPE-2 reply (0102 01000000 9421d811) is tolerated by the client.

FAMILY ID: 0x11D82194
  Appears in every lobby frame. Believed to be the ClientOut (client->server)
  pool identifier. Whether a distinct ClientIn pool id exists in 1.74 is
  UNRESOLVED - see open questions.

FAMILY REGISTRATION: RVA 0x2CF0060
  Contains 4 receive variants (01-04) and the ASCII name "0x11d82194".
  Descriptors carry schema fields and parse-function code pointers
  (0x4A0450, 0x56CA50). This was found independently of the VoiceChat trail
  and is genuinely lobby-side. GOOD STARTING POINT.

DISPATCHER: RVA 0x41DB60  (verified in IDA, lobby-side, trustworthy)
  Gate conditions:
      msgid != 0
      msgid <= 0x4F0
      conn+0x20 == 6                (connection state)
      conn+0x10 <= small value
      handler list at conn+0x250 non-empty
  conn+0x250 is an INTRUSIVE DOUBLY-LINKED LIST HEAD. It is empty iff
  [conn+0x250] == conn+0x250 (the classic "cmp [r13], r13" idiom).

  What the dispatcher actually does (from the 0x41DE27 region):
      movsxd rbp, [rsi]           ; msgid
      lea    rcx, [rdi + 0x260]   ; allocator pool on the connection
      call   0x41B7C0             ; allocate a record (this is an ALLOCATOR,
                                  ;   NOT a handler lookup - older notes had
                                  ;   this wrong)
      mov    [rbx + 4], ebp       ; record+4 = msgid
      call   0x24E8B70            ; memcpy(record+0x18, payload, size)
      ... intrusive list insert onto conn+0x250 ...

  KEY POINT: the dispatcher only QUEUES. It never calls a handler. Something
  else drains that list asynchronously and invokes the handler. THAT DRAINER
  HAS NOT BEEN FOUND, and finding it is probably the most valuable next step
  (see Section 4).

SESSION OBJECT (found by vtable scan; lobby-side)
  vtable window : 0x26160A0 .. 0x26162A0
  session vtable: 0x2616260
    +0x60  status  (2 = reject, 7 = accept, 0 = waiting)
    +0x70  state   (small enum 0..7; anything larger means the object is dead
                    and the heap slot was reused - ALWAYS liveness-check this)
    +0x98  delivered-message slot
    +0x1A0 cn (32 bytes)
    +0x1C0 sn (32 bytes)
    +0x2F0, +0x2F8 markers

  Observed reject cycle on a park:
      state=6 status=6  ->  status=2 (verdict, ~1.1s later)  ->  status=0

  Completion callback  RVA 0xE38590 (session vtable slot 1):
      reads [session+0x60]; 7 -> success continuation 0xE39C20,
      0 -> keep waiting, anything else -> fail 0xE39A80
  Success() RVA 0xE38600 sets status = 7
  state>2 predicate RVA 0xE38620

##  SECTION 2B: LIVE WIRE EXPERIMENTS (2026-08-25) - msgid 0x003 and limits
################################################################################

After the VoiceChat correction the reply msgid was known to be unfounded
(0x100/0x101/0x102 came from VoiceChat's table). A series of live experiments
followed. Results, in order:

MSGID SWEEP (reply id 0x001..0x090, one per connection)
  Every id closed the socket at 0.00s after the reply - EXCEPT 0x003, which
  held it open. Reproduced repeatedly:
      0x003 held= 20.02s,  4 exchanges
      0x003 held=234.79s, 46 exchanges
      0x003 held= 78.45s, 15 exchanges
  With 0x003 the client polls its 2-byte 0103 frame indefinitely and the
  server answers each one; the connection survives to the 300s server-side
  timeout instead of dying instantly.

IN-CONNECTION PROBE SWEEP (0x003 keepalive + one probe id per exchange)
  Failed immediately and informatively: sending ANY other msgid down the live
  socket collapses it in ~5s. 234s/46 exchanges without probes became
  5.01s/1 exchange with. 0x003 is the ONLY tolerated id.

BODY IRRELEVANCE (accidental but clean)
  A gating bug meant every reply in one run carried an EMPTY body instead of
  the 168-byte captured bgs blob. Client behaviour was identical - same 300s
  hold, same endless 0103 polling. THE BODY IS NOT BEING PARSED.

SHORT-FRAME SWEEP (2-byte [01][XX] replies, XX = 0x00..0x08)
  Rationale: the client's 0103 is a 2-byte control frame with no counter and
  no family id, unlike its 10-byte 0100 - answering it with a 180-byte
  protobuf envelope may be a category error.
  Result: all closed at 0.00s except echoing 0103 back, which bought 5.00s
  and one exchange. Not a state change.

INTERPRETATION
  0x003 is almost certainly a benign/ignored id that fails to trip the
  validation-failure teardown path, NOT a handshake step. The client has
  never demonstrably consumed anything the server sent. Treat 0x003 as a
  useful keepalive that buys a long-lived socket for experimentation, and
  nothing more.

  Practical value: with 0x003 you get a stable 300-second connection instead
  of an instant disconnect. That is a much better platform for any future
  experiment than reconnecting for every trial.

##  SECTION 2C: REAL BLIZZARD LOBBY TRAFFIC DECRYPTED (2026-08-25)
################################################################################

A packet capture of a genuine Overwatch 1 lobby session (retail, client
192.168.3.44 -> Blizzard 37.244.13.27:3724) was obtained together with a dump
of the connection's four 64-byte key slots. The client->server direction has
been FULLY DECRYPTED: 211 frames, 61,712 of 61,712 bytes, zero parse errors.
The server->client direction is ALSO fully decrypted: 94 frames, 383,890 of
383,890 bytes, 100%. This is the first known plaintext of real OW1 lobby
traffic in either direction.

  The s2c key was contributed by **Zagrion** (AyakaPS Discrd) within
  hours of this project being published, after he redid the TCP reassembly with
  tshark. The key had been tried and rejected locally because a hand-rolled
  scapy reassembly mishandled overlapping retransmits - one byte of
  misalignment destroys a stream cipher downstream. Use tshark:
      tshark -r capture.pcap -q -z follow,tcp,raw,0

KEY SCHEDULE - CONFIRMED AGAINST REAL TRAFFIC
    MAC1            = HMAC-SHA256(k0, cn || sn)     (client -> server)
    MAC2            = HMAC-SHA256(k1, sn || cn)     (server -> client)
    c2s cipher key  = HMAC-SHA256(k3, sn || cn)     (JAM key, client->server)
    s2c cipher key  = HMAC-SHA256(k2, cn || sn)     (JAM key, server->client)

  Four separate 64-byte key slots, one role each. In tournament mode all four
  are zero, which is why lobbyserv's ZERO_KEY works locally - but the general
  structure is the above. k0..k3 come from the Battle.net session; they are not
  derivable from the handshake.

TRUE SERVER PREAMBLE (byte offsets in the reassembled stream)
    [  0] "HELLO PRO SERVER\0"            17 bytes
    [ 17] srv_rand                        32 bytes
    [ 49] difficulty                       1 byte   (0x09 here, 0x07 in another
                                                     capture; lobbyserv sends 0)
    [ 50] sn                              32 bytes

                                                        real server

  NOTE: 2-byte 0x0000 packets appear in the capture before HELLO, before the
  65-byte block and before MAC2. These are CAPTURE ARTIFACTS - they carry the
  same TCP sequence numbers as the real packets (duplicate/window probes) and
  are NOT protocol bytes. lobbyserv's preamble shape is correct as-is.

FRAME FORMAT
    [u24be frame_len][u16be msgid][ ... ]
  The third field is MSGID-DEPENDENT and there is NO general rule.
  Measured: on client->server 0x4401 frames it is a u32le payload length,
  96 of 96. On the server->client stream that interpretation holds for only
  19 of 86 frames; 67 do not follow it. Do not assume a length field.
  Some msgids use it as a counter (client 0x5000 increments by 4).

  BARE FRAMES ARE NORMAL, not a special case. The retail server sends six
  two-byte msgid-only frames in one session: 0x0002, 0x2004, and 0x0003 four
  times. Three-byte frames also occur (0x1c0e02, 0x1c0600).

################################################################################
##  SECTION 2D: BARE-FRAME EXPERIMENTS (2026-08-25, post-decryption)
################################################################################

Knowing the real server answers with a bare two-byte frame, lobbyserv was
changed to do the same. Retail ids run 0x0100 below this build's for the low
messages (retail client 0x0000/0x0003 == 1.74 client 0x0100/0x0103), so the
predicted reply was a bare 0x0102.

RESULT: bare 0x0102 does NOT advance the client. But it produced a NEW and
useful behaviour - with 0103 left unanswered, the client retries the 0103 poll
EXACTLY FIVE TIMES and then gives up. That is its natural retry budget, and it
had never been observed cleanly before because the server was always replying
to something.

THE RETRY COUNT IS A DISCRIMINATOR
  Reply with a bare msgid, then stay silent, and count the client's 0103
  retries before it closes:
      0 retries -> frame REJECTED; client tore the socket down immediately
      5 retries -> frame ACCEPTED as structurally valid; client waited out its
                   full budget still expecting a real answer
  This is the sharpest signal the project has ever had. Use it.

SCORES SO FAR
      0x0102  -> 5 retries   (the only value to score above zero)
      0x0001 .. 0x000B -> 0 retries, every one
  Sweep of 0x0001..0x04F0 as bare frames, one msgid per connection, was still
  running at time of writing. Results append to bare_results.txt.

INTERPRETATION - AND THE UNCOMFORTABLE PART
  0x0102 already scores the MAXIMUM. The client accepts that frame as valid
  and still does not advance. If nothing else in the sweep beats 5, the
  conclusion is NOT "wrong msgid" - it is "a bare frame is the wrong SHAPE",
  i.e. the reply needs a payload and the msgid dimension is already maxed out.

  Supporting this: in the real transcript both kinds exist. The bare 0x0002
  ack is immediately followed by 0x3004 carrying 106 bytes. The 1.74 client
  may simply be waiting for the payload-carrying reply, not the ack.

  NEXT EXPERIMENT IF THE SWEEP COMES BACK EMPTY: bare 0x0102 followed by a
  payload-carrying reply modelled on the retail 0x3004 (106 bytes).


################################################################################
##  SECTION 2E: THE ACK IS SOLVED, THE FOLLOW-UP IS NOT (2026-08-25)
################################################################################

BARE MSGID SWEEP - COMPLETE AND CONCLUSIVE
  Method: reply to the client's 10-byte 0100 with a bare two-byte frame
  carrying msgid X, then stay silent. Score = number of 0103 retries the
  client makes before closing.
      0 retries -> frame rejected, immediate teardown
      5 retries -> frame accepted as valid; client waits out its full budget

  Swept 0x0001..0x0152 (338 values), one msgid per connection.
      0x0102  -> 5 retries
      EVERY OTHER VALUE -> 0 retries
  0x0102 was re-tested mid-sweep as a positive control and reproduced its
  score of 5, which validates the harness and the zeros around it.

  >>> THE CORRECT ACK IS A BARE TWO-BYTE FRAME, msgid 0x0102, framed as
  >>>     00 00 02 01 02
  >>> No counter, no family id, no bnet envelope, no body.
  This is the first server->client message the 1.74 client has ever accepted.

PAYLOAD FOLLOW-UP - REJECTED IN EVERY FORM TRIED
  Method: send the accepted bare 0x0102, then on the client's first poll send
  a payload-carrying frame using the REAL retail 0x3004 body (104 bytes,
  verbatim from the decrypted capture), sweeping the follow-up msgid.
  Candidates: 0x3004 0x3104 0x0104 0x0004 0x3005 0x3105 0x1200 0x1300
              0x4401 0x4501 0x1a13 0x1b13
  Result: EVERY candidate collapses the connection at retry #1. Bare ack plus
  silence gets 5 retries; bare ack plus any payload gets 1. Reproduced on a
  second full pass.

  Interpretation: the rejection is content- and msgid-independent, so it
  happens at a framing/validation layer BEFORE msgid dispatch. Note this

##  SECTION 2F: INNER PAYLOAD FORMAT - LENGTH-PREFIXED PROTOBUF (2026-08-25)
################################################################################

Mining the 94 decrypted server frames revealed how message bodies are built.
This is build-independent structure and should transfer to 1.74.

LENGTH-PREFIXED PROTOBUF SUB-BLOCKS
    [u32le block_len][protobuf block]   repeated within a frame body
  356 such blocks were found across the 94 server frames using a strict
  protobuf validator (rejects field 0, wiretypes 3/4/6, and any block that
  does not consume exactly). Examples:

    msgid 0x4e0d  len=10   08ce84011001180c2000
                           -> f1=16974  f2=1  f3=12  f4=0
    msgid 0x4e0d  len=19   08ce8401100118032094d38cbcd496cda68a01
    msgid 0x4e0d  len=20   521209707041000200000211ef9d163a00000000
                           -> f10, len 18
    msgid 0x4e0d  len=29   2a1b + 27 bytes UTF-8
                           -> f5 = "<BattleTag>#<digits>"  (a real player name,
                              decoded from Cyrillic UTF-8; confirms the
                              protobuf reading is correct and not coincidence)

  So a frame body is NOT one monolithic protobuf. It is a sequence of
  u32le-length-prefixed protobuf blocks, interleaved with fixed binary fields.

16-BYTE ENTITY HANDLES
    [u32le id][8 zero bytes][u32le type]
  The session's primary handle 3fe15a42 00000000 00000000 00000001 occurs 37
  times - in 23 of 94 server frames AND in 2 client frames, so handles are
  echoed in both directions. Other observed handles follow the same shape
  (e.g. 00300600 0000000000000000 00000001).

  This is very likely what a 1.74 reply must carry and what makes a
  payload frame valid: an entity handle the client is already holding.
  Compare the failed payload experiment in Section 2E - the retail body was
  byte-exact but carried ANOTHER session's handles.

FRAME FAMILIES (server -> client)
    0x4e0d  x4   282/520/496/134 B - identity + account data, richest protobuf
    0x2800  x8   326-367 B, all start with the same 32 bytes (two handles)
    0x3202  x3   136/62/25 B
    0x3005  x1   21162 B - array: [u32le 56][8-byte records, index 02,03,04...]
                  roughly 2,600 entries. Map/asset manifest.
    0x3004  x1   106 B - the follow-up to the bare ack

################################################################################
##  SECTION 2G: TWO-SESSION DIFF - WHAT IS CONSTANT VS SESSION-SPECIFIC
################################################################################

packets.pcap (AyakaPS/Plasmawatch, client 16390422107773322648) and
login-enc.pcapng are TWO DIFFERENT real lobby sessions. login-enc could not be
decrypted (no keys) but its handshake is plaintext and its frame sizes are
visible, which is enough to separate constant protocol structure from
per-session data.

THE 292-BYTE BLOB IS SESSION-SPECIFIC, NOT FIXED STRUCTURE
  Only 1 of 292 blob bytes match across the two sessions (offset 200, and that
  is coincidence). Concretely:
      blob[0]    0x8A vs 0x43   (NOT 0x02)
      blob[1:5]  random vs random   (NOT 7F 00 00 01)
      blob[255]  0x82 vs 0xA4   (NOT 0xFF)
  So the real blob is cryptographic material - almost certainly the RSA-wrapped
  session key exchange. lobbyserv's blob (blob[0]=0x02, 127.0.0.1, blob[255]=
  0xFF forcing the RSA path to be skipped) is a TOURNAMENT-MODE SHORTCUT that
  only works because zeroed keys let the client skip validating it. It is NOT
  the retail protocol. Section 1's blob construction is correct FOR TOURNAMENT
  MODE only.

DIFFICULTY IS A PER-CONNECTION VALUE
  0x09 in packets.pcap, 0x07 in login-enc. Confirmed variable = proof-of-work
  parameter. lobbyserv sends 0, which the client accepts (no work required).

THE PROTOCOL SKELETON IS INVARIANT ACROSS SESSIONS
  Client packet-size sequence: [17, 40, 40, ~340, ~730, 8, ...]
      17  HELLO PRO CLIENT
      40  [8 pad][32 cn]
      40  [8 pad][32 MAC1]
     ~340 opening message (337 vs 353 B) - carries msgid 0x0000
     ~730 second message
  Server packet-size sequence: [HELLO, 65, 32, 292, 5, ~100, 1300...]
      65   [srv_rand][difficulty][sn]
      32   MAC2
     292   blob
       5   the BARE ACK frame (2-byte msgid, +3 framing) - present in BOTH
     ~100  first payload frame (109 B = 0x3004 in packets.pcap)

  Both sessions match this skeleton exactly. Only the CONTENTS differ.

WHAT THIS MEANS FOR THE 1.74 BLOCKER
  The payload experiment (Section 2E) failed because the retail 0x3004 body was
  another session's bytes - and this diff confirms essentially EVERYTHING inside
  a frame is session-specific: the blob, the opening message, the entity
  handles. There is no "mostly-constant frame with a few fields to swap"; the
  bodies are built fresh per session from session state the 1.74 client has
  and the retail capture does not.

  Consequence: a working 1.74 second message cannot be lifted from any retail
  capture, decrypted or not. It has to be constructed from the 1.74 client's
  OWN state. That is the schema problem, and it is behind Arxan.

##  SECTION 2J: THE REJECT IS A TIMEOUT, NOT A PARSE FAILURE (2026-08-27)
################################################################################

owobs v57 locked onto the real session object (vtbl +0x2616260; the other 44
vtable-window objects are a different class, +0x2616108) and timestamped its
verdict field (session+0x60). The result reframes the whole blocker:

  status=6 (awaiting verdict)  at t=345ms
  status=2 (reject)            at t=5223ms   -- ~5000ms later, EXACTLY
  ... repeats every connection: 5223, 10495, 16519, 23716, 32325, 45205ms
      i.e. a precise ~5.0s dwell at status=6 then flip to 2.

THE reject is a 5-SECOND TIMEOUT, not a validation of our bytes. The client
reaches status=6 (handshake complete, awaiting the next server message that
advances the lobby), waits 5s, does not get what it wants, and times out to
status=2. Every "retries=1" / "retries=5" we measured was this same timeout
window, not a content judgement.

CONSEQUENCE - this changes the problem:
  - Our 0x0102 replies are not being "rejected on content". They are simply not
    being consumed as the message that advances state 6. The client sits
    waiting and times out.
  - So the follow-up the client wants is very likely NOT another 0x01xx frame.
    In the real server stream the message that advanced the client after the
    bare 0x0002 ack was 0x3004 - a DIFFERENT channel. The advancing message is
    probably in a different family (0x30xx / 0x1c / 0x4e), not 0x02.
  - The bare 0x0102 ack was still correct (it is what the client accepted at the
    2-byte stage). The missing piece is the SECOND server message, and it is a
    different channel than we have been sweeping.

NEXT: after the bare 0x0102 ack, send a 0x3004-channel message (the real
  server's actual follow-up), then the other observed families, and watch

METHOD NOTE: session+0x60 verdict watching (v57) is the key instrument - it
  distinguishes "timed out waiting" (flat 5s then 2) from "parsed and rejected"

##  SECTION 2L: OUR FRAME IS RECEIVED+DECRYPTED+DECODED (marker scan) 2026-08-27
################################################################################

owobs v60 (read-only, zero risk) + lobbyserv v139 marker frame settled the fork
left open by the timeout (2J): is our follow-up frame dropped BEFORE decode, or
received-but-not-consumed?

METHOD: lobbyserv sends, after the bare 0x0102 ack, a follow-up on channel
  0x3004 whose body is the 16-byte marker DEADBEEFCAFEF00D5EEDFACE1337C0DE
  repeated x4 (sent JAM-encrypted). owobs scans writable memory for the
  PLAINTEXT marker.

RESULT: MARKER FOUND, every connection, in a private RW region (0x40000-sized,
  prot=PAGE_READWRITE), at a stable offset. Context bytes immediately before
  the marker payload:
      ...00 00 00 42 30 04 | deadbeef.... (marker)
  -> 0x3004 = our msgid, 0x42 = 66 = parsed body length. The client stored our
  frame in a STRUCTURED decode buffer with msgid and length broken out.

CONCLUSION - the block is DOWNSTREAM of decode:
  - Our frame is received, JAM-decrypted, and decoded into the client's message
    buffer with its envelope (msgid+len) parsed. Not dropped at socket/cipher/
    framing. The "before decode" hypothesis is FALSE.
  - Yet session status stays 6 and times out (2J). So the decoded message is
    either (a) not routed to the state-6 handler (dispatch gate), or (b) routed
    but the handler rejects/ignores it as not-the-awaited-message.
  - This is the "decoded but not consumed" branch, now confirmed. The remaining
    unknown is the dispatch/consume condition - which is the decrypted LOGIC the
    DR hook (2K) could not safely observe.

The receive/decode buffer is a stable RW private region (per-run address, e.g.
  0x0000004C724C0000 + ~0x3AE25). A page-guard on THIS data page (VirtualProtect

  READS our decoded frame - i.e. the dispatcher/consumer - giving the return
  address of the consume path WITHOUT a debug register. This is the stealth
  hook 2K asked for, now with a concrete target.

  - The client ALSO runs a 0x0103 poll loop waiting for the actual response

  - So the client sits at "ENTERING GAME" (verdict accepted) but never fully
    proceeds (poll loop unsatisfied).

CONNECTION-HOLDING SOLVED
  - Silent polls -> client closes after 5 retries. Responding to every 0x0103

    (tested 36+ retries). This gives Success() time to fire on a live socket.

THE REMAINING WALL: the poll wants a RESPONSE we can't yet form

    EMPTY body closes it. Keepalives (0x0003) never close it.
  - So the client rejects the content frame itself, not just a bad body.
    Leading theory: JAM cipher COUNTER DESYNC. The cipher is a stream (counter
    advances per byte). Keepalives stay in sync, but a content frame the client
    tries to DECODE surfaces the desync as a garbage body -> close.

RETAIL GROUND TRUTH (from Zagrion's decoded capture + our streams)
  Server: 0x0002(ack) -> 0x3004 -> 0x3005 -> 0x1c0e -> 0x4e0d

  - The server's 0x3004 (right after ack) is likely what unblocks the client.

  - state (+0x70): the overall lobby progression (6 = awaiting the advancing
    message). NOT driven by the verdict machinery. Nothing we call (Success,
    completion, continuation) moves it past 6.
  => state 6->7 is gated on the REAL second message being consumed through the

    0x4A0450   NOT a message parse function. It is a constructor/initializer
               loop over 0x58-byte objects that stores the constant
               0x800000000000000F into obj+0x40. That constant shows up in
               memory scans as a false-positive "key".
    0x56CA50   NOT a message parse function. STL container internals -
               uninitialized_copy / move loops striding 0x40-byte elements.
    0x41B7C0   NOT a handler lookup. It is a size-class ALLOCATOR, called by
               the dispatcher to allocate the queued message record.
    sub_84B668 / sub_76854B  Arxan-obfuscated blobs. Whole-function views
               produce junk (enter with absurd operands, sar ch/0, imul with
               garbage displacements). Individual basic blocks disassemble
               fine; function entries do not.

VOID THEORY: "the server must echo an 8-byte pending-connect token that the
client holds in memory". That is a real mechanism - in the VOICE CHAT client.
There is no evidence the lobby protocol works this way.

For reference, the VC mechanism decoded correctly (may help if anyone ever
wants local voice chat):
    map object   = handler's arg1 - 8   (multiple-inheritance base fixup;
                   the manager has a vtable at +0 and a second at +8)
    list head    = [map + 0x1D8]
    entry layout : vtable @ +0, next @ +0x10, key @ +0x18,
                   flag BYTE @ +0x28 (must be 0), state @ +0x40
    type check   : virtual call [entry_vtable + 8] compared to the tag global
    on accept    : ResponseConnect writes msg+0x18/+0x1C to entry+0xF0/+0xF4
                   and sets entry+0x40 = 4
                   ResponseLogin  writes msg+0x18/+0x1C to entry+0x170/+0x174
                   and sets entry+0x40 = 6
    So 4 = connected, 6 = logged in, and the entry is at least 0x178 bytes.

ALSO VOID: owobs versions v41 through v47. Every one of them hunted the VC
pending map. The scanning machinery (session finder, liveness gating, poison
filtering, region dumping) is reusable; the targets are not.


################################################################################
##  SECTION 4: OPEN QUESTIONS / WHERE TO GO NEXT
################################################################################

Ordered by estimated value.

1. FIND THE LOBBY HANDLER TABLE.
   The dispatcher requires a non-empty list at conn+0x250 for the LOBBY
   connection. Something registers lobby handlers into it. Find that
   registration and you have the real equivalents of the functions in
   Section 3.
   Approach: start from the family registration at 0x2CF0060 (genuinely
   lobby-side). In IDA, Shift+F12 for strings, look for lobby-domain names
   (Lobby, Party, GameServer, EnterGame, Matchmaking, Queue).

2. FIND THE QUEUE DRAINER.
   The dispatcher queues records onto conn+0x250 and returns. Whatever pops
   that list and calls the handler is the function that constructs the
   handler's "this". In IDA, text-search (Alt+T) for 250h and look for a
   function that walks [reg+0x250], follows [node+8] links, and ends in an
   indirect call.
   Caveat: much of this region is Arxan-obfuscated. Attempting to view the
   containing function start (e.g. sub_84B668) yields junk instructions
   (enter with absurd operands, sar ch,0, imul with garbage displacements).
   Individual basic blocks disassemble fine; whole-function views do not.

3. WHAT IS THE SECOND SERVER MESSAGE?  <-- THE CENTRAL QUESTION
   The first one is now known: a bare two-byte 0x0102 (see Section 2E). The
   client accepts it and waits out five 0103 retries expecting more. Nothing
   sent after it has ever been accepted.

3b. (historical framing) WHAT DOES THE 0103 FRAME ACTUALLY WANT?
   The client sends 0100 (10 bytes: msgid + counter + family) then 0103
   (2 bytes, no counter, no family), then closes unless answered with msgid
   0x003. Everything tried so far - protobuf envelopes with the captured bgs
   body, empty bodies, error statuses, 2-byte control frames across
   0x00..0x08, and 1,264 candidate msgids - leaves it polling forever or
   tears the socket down. Three independent implementers have reached this
   exact point and none has passed it.
   The reply grammar is still unknown. This is the whole problem.

4. IS THERE A DISTINCT ClientIn POOL ID?
   All replies stamp family 0x11D82194, which is likely the ClientOut
   (client->server) identifier. If server->client frames need a different
   pool id, every reply ever sent has been rejected at the family router.
   Approach: scan for the strings "ClientInLobbyConnect" /
   "ClientOutLobbyConnect", locate the pool objects, read their CRCs.
   Cross-check against overtools CRC32 string lists.

5. POST-CONNECT PATH TO THE MENU.
   Entirely unexplored. On OW 0.8 beta the server proactively pushes
   ClientInLobbyConnect messages (ids 20503/20504/20505, channel 10) to drive
   DISCONNECTED -> CONNECTED -> menu. On 1.74, pushing BEFORE the client's own
   connect request races it and causes immediate teardown (verified). If
   pushing applies at all here, it is POST-connect.

6. LOOTBOXES???
   Not started. Presumably needs an inventory service response. Beyond all of
   the above.


################################################################################
##  SECTION 5: RULED OUT - DO NOT RETRY
################################################################################

- PROACTIVE PUSH BEFORE CONNECT. Sending server->client messages before the
  client issues its own connect request races it; the client tears down the
  socket. An observe-only build confirmed the client behaves normally when the
  server stays quiet. Reply, do not push.

- FORCING THE VERDICT FIELD (session+0x60 = 7). Six variants tried: hold from
  park, pin on send, reactive flip, sustained hold, pin on the 0103 frame.
  The flip works mechanically (Arxan does not object to the heap write) and
  the client's retry loop even stops - but it then stalls, and the socket
  still closes. Socket close is a transport/protocol decision decoupled from
  the verdict dword, and the flip cannot conjure the session data the menu
  path needs. DEAD END.

- DERIVING A TOKEN FROM THE HANDSHAKE NONCES. HMAC-SHA256, SHA256, FNV-1a,
  FNV-1, CRC32, djb2, SDBM, joaat tested over cn/sn in many orderings.
  No match to anything. (Also: this was chasing the VoiceChat token.)

- INLINE CODE HOOKING INSIDE Overwatch.exe. See Section 1 - blanket
  VirtualProtect denial, all 11,408 executable pages.

- x64dbg + ScyllaHide. Defeated by Arxan at every preset.

- USING DUMP .rdata ADDRESSES. Encrypted and shifted ~0x10000. Code only.

- IDA ON THE pe-sieve DUMP AS A GENERAL SOLVENT. Worth doing - it caught the
  VoiceChat misidentification and confirmed the 0x85FFE0 offsets - but it does
  NOT get past the two real obstacles. Indirect calls go through vtables in
  encrypted .rdata so xrefs do not resolve, and function entries are
  control-flow-flattened so whole-function views are junk. Expect to read
  individual basic blocks, not functions.

- REPLY MSGIDS OTHER THAN 0x003. All of 0x001..0x090 tested as the main reply;
  all close the socket at 0.00s. Any non-0x003 id sent down a live 0x003
  connection collapses it within ~5s.

- VARYING THE REPLY BODY. Empty body and the 168-byte captured bgs body
  produce identical client behaviour. The body is not being parsed.

- COMMAND-LINE FLAGS --key AND --QuickLogin. The client's connect frame is
  byte-identical (0100 01000000 9421d811) regardless of --key value, so --key
  does not reach the lobby handshake despite its help text ("connection key
  for the server"). --QuickLogin changes nothing at this stage either.
  Note: there is NO log-level flag in this build; the full option list has
  been checked. Lobby-side logging cannot be turned on from the command line.

- CLIENT-SIDE STATE FORCING A LA PROMETHEUS (saturn-xvi/prometheus, artpop2).
  That project reaches the menu on OW 0.8 BETA by patching anti-debug and
  forcing client state, with no server implementation at all. On 0.8 the
  client boots to a menu regardless of server. On 1.74 it does NOT - it hard
  blocks waiting for a server reply. Their technique also relies on inline
  code patching, which 1.74's Arxan blocks outright. Their code contains no
  login/connect/server logic whatsoever, so there is nothing to port. (Is what I believe)
