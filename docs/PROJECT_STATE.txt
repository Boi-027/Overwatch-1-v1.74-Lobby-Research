ADDRESS CONVENTION - CORRECTED (rev 18)
  Addresses in this document are RVAs (offsets from the module base). In a
  pe-sieve process dump they are ALSO the file offsets - verified: the
  Success() signature 48 83 C1 F0 BA 07 sits at file offset 0xE38600, which
  is the value this document calls RVA 0xE38600. Do NOT apply a section
  delta when reading the dump with a hex editor or a script. (The PE section
  headers claim raw != virtual; empirically the dump does not follow them.)
  Runtime address = module base + RVA.

Rev 18 invalidates several things asserted in rev 17 and earlier. If you have
an older copy, discard the following.

(1) THE VOICECHAT MISIDENTIFICATION (2026-08-25, still applies)
    0x86BEE0 "ResponseConnect", 0x86F432 "ResponseLogin", the names table at
    0x261AB68, and the pending-connect-token theory all belong to the VOICE
    CHAT client, not the lobby. Full detail in Section 8 (VOID).

    Dump the whole names table. If the neighbours are audio devices, stop.

(2) 0x41DB60 IS NOT A MESSAGE DISPATCHER  ★ NEW, rev 18
    Rev 17 described it as the JAM dispatcher with a "handler list" at
    conn+0x250. It is the OUTBOUND SEND-QUEUE ENQUEUE. See Section 3.
    Consequently:
      - conn+0x250 is a TX buffer chain, not a handler list.
      - The "msgid <= 0x4F0" gate is a MAX WRITE SIZE of 1264 bytes. The
        value tested is a LENGTH, not a msgid.
      - Rev 17 Section 4 items 1 and 2 ("find the lobby handler table",
        "find the queue drainer") were chasing the transmit path. VOID.
      - The 2E sweep of "1,264 candidate msgids" got its size from a byte
        cap by coincidence.

(3) +0x439904 IS NOT A DRAIN+DISPATCH CORE  ★ NEW, rev 18
    Rev 17 Section 2V described it as the drain-and-dispatch core with a
    "cmp [rcx+0x20], 0x32" gate. Decompiled: it is a small bool predicate
    that checks a global flag, calls a generic accessor, does one virtual
    call as a type query, and tests obj+0x250 non-null. No dispatch, no list
    walk. The 0x32 gate does not exist - it came from a hand-rolled
    disassembler misreading bytes.

(4) THE 11-NAME "LOBBYSYSTEM HANDLER FAMILY" WAS FABRICATED  ★ NEW, rev 18
    Rev 17 Section 2V listed eleven LobbySystem_C::__* strings. Only FOUR
    such strings exist in the binary:
        LobbySystem
        LobbySystem_C::LobbyConnectHelloErrorHandler
        LobbySystem_C::LobbyDisconnectClientHandler
        ClientLobbyMessageSystem_C::__LobbyServerConnectionUp
    __LobbyServerLoginResponse, __LobbyServerHelloReceived, and the rest were
    never in the data. Any reasoning built on that flow is unfounded.
    Also: the only code reference to these strings is a logger with format
    "[%s] %s - %s". Dispatch is by id/vtable slot, not by name - searching
    for handlers by name will not work.

(5) .rdata IS DECRYPTED IN A PROCESS DUMP  ★ NEW, rev 18
    Rev 17 Section 5 says "USING DUMP .rdata ADDRESSES. Encrypted and shifted
    ~0x10000. Code only." That is FALSE for a pe-sieve dump of the running
    process. Measured: .rdata entropy 5.713, 27% printable, lobby strings
    readable in the clear. The live-.rdata-snapshot tooling (owobs v49-v52)
    is no longer needed for static work.
    .data IS truncated in the dump (0x24B800 of 0x83E5A4), so .data addresses
    past ~0x2EE3600 are absent. .text and .rdata are complete.

(6) THE CIPHER-DESYNC THEORY IS DEAD  ★ NEW, rev 18
    Rev 17 Section 2M proposed a JAM counter desync on content frames.
    Disproved twice over:
      - The entire 383,890-byte retail server stream decrypts in ONE
        continuous pass, 94 frames, zero parse errors. The s2c keystream is
        continuous across the whole session; there is no per-frame reset.
      - Answering every poll with a bare frame stays in sync for 40+
        consecutive frames.
    When a content frame closes the client it is not cipher state.

(7) HOW THE 2E SWEEP MUST BE READ  ★ NEW, rev 18
    That sweep REPLACED the ack with the candidate msgid. A msgid scoring 0
    there means "this is not the ack", NOT "this msgid is rejected on its
    merits" - the client tore down because it was never acked at all.
    2E establishes exactly one thing: 0x0102 is the ack.

(8) srv_dec.bin DOES NOT PARSE FROM BYTE 0  ★ NEW, rev 18
    The README's reading snippet works on cli_dec.bin and fails on
    srv_dec.bin. The server stream parses only from offset 292:
        off = 292
    From there: exactly 94 frames, 383890/383890, zero errors. The first 292
    bytes are the decrypted state blob.

##  SECTION 1: SOLVED AND VERIFIED
################################################################################

[SOLVED] JAM cipher - reimplemented server-side in lobbyserv.py (Jam class).
  Known-answer test (independently confirmed by two other implementers):
    key    = 00 01 02 ... 1f
    first 64 bytes of keystream:
      f07e5df1c8d51c0d754da6ddde34cca01db0ed26334eb94ae277135a0764c6a6
      794d7ab0cc0978ef43de30766a7ee1d7c90e159df239d4016d450fa3d8207842

[SOLVED] Key schedule - VERIFIED END TO END against a real capture.
    MAC1            = HMAC-SHA256(k0, cn || sn)     (client -> server)
    MAC2            = HMAC-SHA256(k1, sn || cn)     (server -> client)
    c2s cipher key  = HMAC-SHA256(k3, sn || cn)
    s2c cipher key  = HMAC-SHA256(k2, cn || sn)
  Four 64-byte key slots from the Battle.net session. Tournament mode zeroes
  all four, which is why ZERO_KEY works locally.
  Verification (rev 18): using the k0-k3 published with packets.pcap, MAC1
  verifies with k0, MAC2 with k1, and the blob decrypts BYTE-IDENTICAL to the
  first 292 bytes of srv_dec.bin. The schedule above is correct, not assumed.

[SOLVED] Handshake to state 6.
    C->S  "HELLO PRO CLIENT\0"                  (17 bytes)
    S->C  "HELLO PRO SERVER\0"                  (17 bytes)
    C->S  [u64 client id][32-byte cn]           (40 bytes)
    S->C  [32-byte challenge][1 byte difficulty][32-byte sn]   (65 bytes)
    C->S  [u64 counter][32-byte MAC1]           (40 bytes)
    S->C  MAC2 || JAM(blob)
  Field names confirmed independently by Sidiusz, who reconstructed the same
  layout. The first 8 bytes of frame 1 are a CLIENT ID (the value published
  alongside packets.pcap as "Client ID: 16390422107773322648"). The first 8
  bytes of frame 3 are a PROOF-OF-WORK COUNTER whose size scales with the
  difficulty byte - measured: difficulty 7 -> counter 944, difficulty 9 ->
  counter 180. lobbyserv sends difficulty 0, which the client accepts with no
  work required.

  CRITICAL: MAC2 and the blob are ONE CONTINUOUS cipher stream. Do not
  reinitialize JAM between them; the partial-block keystream must carry over.
  Encrypt all 292 blob bytes in the same stream, offset 0, no header.
  Getting this wrong produces a client that decrypts the blob, counts all 292
  bytes, and silently closes - a very confusing failure mode. (Sidiusz lost
  time to exactly this; so did we.)

[SOLVED] 292-byte state blob (TOURNAMENT MODE ONLY).
  BLOB_KEY (64 bytes):
    35 86 F3 62 8A 63 1B 70 57 12 40 5B 8A CC 71 D4
    0F D1 67 0C C1 B0 3E A3 84 97 4A 6F B1 A7 61 96
    B1 42 F0 B7 23 10 EA 81 16 D0 0A 4C 35 2F 09 AC
    DB FB 50 A6 3E C5 15 3E 62 E4 D6 7F E0 9B EE CC
  Construction:
    256-byte body, body[i] = i & 0xFF
    body[0]        = 0x02
    body[1:5]      = 7F 00 00 01        (127.0.0.1)
    body[255]      = 0xFF               (forces blob >= n, RSA path skipped)
    body[176:208]  = HMAC-SHA256(BLOB_KEY, body[0:176] + body[208:256])
    + 36 trailing zero bytes            => 292 bytes
  Sidiusz's independent implementation is byte-identical, including the 36
  zero trailer, and he confirms zero is sufficient to reach state 6.
  NOTE: the REAL blob is session-specific RSA material - in the decrypted
  capture bytes 0..255 are high entropy and the 36-byte trailer is structured
  (3388fd09 00050001 8469000000000000 / 3388fd09 000d0001 00008c0e /
  0a394366 cc680100). Our construction is a tournament-mode shortcut that
  works only because zeroed keys let the client skip validating it.

[SOLVED] Counter gate on the first reply.
  conn+0x88 initializes to 1 and a reply's index must be BELOW it, so the
  first server reply must carry counter = 0. (01 00 00 00 encodes 1, not 0 -
  this off-by-one silently killed every reply for weeks.)

[SOLVED] Injection chain that survives Arxan.
  bink2w64.dll (proxy) -> loads bink2w64_original.dll + your DLLs.
  ALL ~75 Bink exports must be forwarded via
    #pragma comment(linker, "/export:NAME=bink2w64_original.NAME")
  A single missing export produces "Failed to load" before your code runs.
  Verify with: dumpbin /exports bink2w64.dll

[SOLVED] Arxan constraints - what works and what does not.
  - VirtualProtect on Overwatch.exe .text: BLOCKED. 11,408 of 11,408 pages
    denied, err=87. Inline hooking is impossible inside the game module.
    MH_EnableHook returns error 10 (MH_ERROR_MEMORY_PROTECT).
    Sidiusz independently hit the same wall (ACG / STATUS_INVALID_PAGE_
    PROTECTION on rwx/rw/writecopy) and reached the same conclusion.
  - Inline hooking of EXTERNAL modules (winmm.dll etc.) works.
  - HEAP WRITES work with no Arxan reaction.
  - CALLING game functions from an injected thread WORKS. Proven twice:
    Success() at 0xE38600, and Keyring::LoadFromBuffer at 0x391DD0 with a
    constructed 9.5 KB argument (Section 6). This is the single most useful
    capability we have.
  - SuspendThread trips the watchdog.
  - Hardware breakpoints (DR registers) are detected; even a one-shot
    arm-then-disarm kills the process. DEAD, do not retry.
  - x64dbg + ScyllaHide: defeated at every preset.

[SOLVED] .pdata gives exact function boundaries.  ★ NEW, rev 18
  The dump's exception directory sits at RVA 0x34D8000 (file offset the same)
  and yields 165,412 RUNTIME_FUNCTION entries (BeginAddress, EndAddress,
  UnwindData; 12 bytes each). This removes all guesswork about where
  functions start and end - use it for every disassembly. Parse:
      for i in range(0x1E4A10//12):
          b,e,u = struct.unpack_from('<III', B, 0x34D8000 + i*12)


################################################################################
##  SECTION 2: THE JAM MESSAGE SYSTEM - FULLY MAPPED  ★ NEW, rev 18
################################################################################

JAM = "Joe's Advanced Messages" (Joe Rumsey, presented publicly in 2013; used
in WoW and Overwatch, different versions). The structures below were derived
independently from the 1.74 dump and then cross-validated field-for-field
against Prometheus's JAM.h (github.com/BreakingBread0/prometheus), which
documents the same system on OW 0.8 beta.

JamMessageInfo  (the per-message registration record, 0x20 bytes)
    +0x00  char* message_name       (stripped in 1.74 - all point to one
                                     placeholder at RVA 0x25E1640)
    +0x08  char* message_protocol   (also stripped; printed as %x in 0.8's
                                     tooling, so it may be an id, not a name)
    +0x10  JamMessageItemInfo* items
    +0x18  u32 crc                  }  read together as a qword this is
    +0x1C  u32 message_id           }  (message_id << 32) | crc

JamMessageItemInfo  (per-field record; 0x30 stride in 1.74, 0x28 in 0.8)
    +0x00  char* name_str           (stripped in 1.74)
    +0x08  u32 message_type
    +0x0C  u32 offset               (relative to the JamMessage object)
    +0x10  u32 size
    +0x14  u32 has_extra_flag       (0xFFFFFFFF on the last field)
    +0x18  JamMessageItemInfo* inner_data_ptr   (nested struct layout)
    +0x20  void* "decoding_func"    -- MISNOMER, see below
    +0x28  (extra qword, 1.74 only; observed 0x20/0x80/0xA0)

  ★ The +0x20 pointer is NOT a decoder. Disassembled: the ones sampled are
    std::vector::resize thunks (this = {ptr,size}, arg = new count, scaling
    by 4 or 8 for the element type, shrink -> destroy-range, grow -> reserve
    + memset). It is present ONLY on ARRAY-typed fields and its presence is
    how you tell a repeated field from a scalar. `size` on such a field is
    the ELEMENT size.
    Consequence: lobby msg 1 is a REPEATED u32, not a scalar u32.
    ClientInLobbyConnect 20504/20505 are REPEATED doubles.

  ★ Terminator: a record with message_type == 17 (END) ends the list. Do not
    rely on has_extra_flag for termination - 0.8's own tooling loops
    `while (item->message_type != 0x11)`.

FIELD TYPE ENUM (authoritative, from Prometheus's jam_messagedetail_window.h)
     0        BOOL
     1,2,3    BYTE
     4,5      SHORT
     6,7      INT (u32)
     8,11     DOUBLE          <-- NOT a u64; corrected rev 18
     9        QWORD
    10        FLOAT
    12        STRING_ARR
    13        STRING
    14        STRUCT          (has inner_data_ptr)
    15        object?
    16        DYNAMIC
    17        END

JamPoolVtable - 1.74 LAYOUT  ★ CORRECTED rev 19
  ★ THE ADDRESS A POOL OBJECT STORES AT +0x00 IS 8 BYTES BELOW WHAT THE
    rev-18 VTABLE SCAN RECORDED. All slot numbers below are relative to the
    address objects actually hold. rev 18's table was built from the +8
    address and every slot index in it was one too low.
    lobby: objects store 0x2609D58; rev 18 recorded 0x2609D60.
    slot 0  destructor_1
    slot 1  destructor_outer
    slot 2  (per-protocol, small)
    slot 3  pool_crc()      -> u32     `mov eax,imm32; ret`
    slot 4  returns_zero()
    slot 5  min_msgId()     -> short
    slot 6  max_msgId()     -> short   (EXCLUSIVE)
    slot 7  allocate_pool(pool, msgId) -> JamMessage*
    slot 8  (shared across all pools, RVA 0x4CC9B0)
    slot 9  per-protocol op taking an existing JamMessage*
  Verified on two protocols:
    LOBBY    0x2609D58  crc=11D82194 min=1     max=5      alloc=0x56CF50
    ClientIn 0x25FEC40  crc=F5FF548A min=20500 max=20510  alloc=0x475380
  slot 7 locks pool+0xA8, allocates from pool+0x10, then switches on the
  msgId to construct the right message class.
  slot 9 calls 0x565260 (get_message_info()->message_id) on its rdx argument
  and switches on that, so it operates on an already-built message.

POOL OBJECT LAYOUT (rev 19, live)
    +0x00  vtable (see above)
    +0x08  u32 refcount/among two u32s
    +0x10  allocator; also a shared .data ptr identical across every pool
           (RVA 0x2E51610 - a hashed string table, NOT the subsystem)
    +0x18  u32 max message object size for this pool, then 0x80
           lobby 0xA0, ClientInLobbyConnect 0x158 - the latter matches
           msg 20500's schema extent (ends 0x157) exactly
    +0x28/+0x30, +0x38/+0x40  intrusive list heads (self-referential = empty)
    +0xA8  the pool's lock

PROTOCOL DESCRIPTOR (a struct, and also a message field type)
    +0x00  m_protocolCRC      u32
    +0x04  m_messageBase      u32
    +0x08  m_messageMax       u32   (EXCLUSIVE)
    +0x0C  m_protocolFlags    u32
    +0x10  m_untrustedServer  u32
    +0x18  m_protocolName     (0x28-byte string object)
  Field names live at RVA 0x2609E78..0x2609ED0. Total size 0x40.
  The lobby's instance is at RVA 0x2609CC8: CRC 0x11D82194, base 1, max 5,
  flags 0.

★ WIRE MSGID ENCODING
    wire_msgid = (channel << 8) | (message_id - pool_messageBase)
  Evidence: retail's decrypted server stream groups cleanly by high byte
  (0x1c02/0x1c05/0x1c06/0x1c09/0x1c0b/0x1c0c/0x1c0d/0x1c0e/0x1c14/0x1c15 is
  one pool; likewise 0x2a02/0x2a05/0x2a06 and 0x4e00/0x4e04/0x4e0d), and the
  1.74 lobby's message ids 1..4 appear on the wire as 0x0101..0x0104 with the
  lobby on channel 1. Retail runs the lobby on channel 0 (client sends
  0x0000/0x0003), so CHANNEL ASSIGNMENT IS DYNAMIC, not fixed per pool.

★ THE WIRE ENCODING IS NOT THE STRUCT LAYOUT
  Tested: for retail messages whose fields are all fixed-size, the observed
  body length should equal the schema extent if bodies were flat struct
  dumps. 22 of 28 retail channels have NO candidate pool under that
  assumption. Combined with Section 5's finding that real bodies are
  [u32le block_len][block] sequences, the encoder does real serialisation.
  The schemas tell you what fields exist and in what order. They do NOT tell
  you how they serialise. Every body we constructed from flat struct layouts
  was wrong in form regardless of content.
  The generic encoder (the "binary decoding" path from the JamMessage
  metadata strings) has not been located; its strings have no resolvable
  xrefs.

##  SECTION 3: THE TRANSPORT LAYER - conn+0x250 IS THE SEND QUEUE
################################################################################

0x41DB60 - ENQUEUE FOR SEND (not a dispatcher)
    41DB60  test r8d,r8d / jle 41DF93         ; count <= 0 -> out
    41DB85  lea rsi,[rdx+0x10]                ; rdx = {+0x00 data, +0x10 len}
    41DBA0  mov eax,[rsi]                     ; LENGTH, not a msgid
    41DBAD  je 41DF4A                         ; zero length -> reject
    41DBB3  cmp [rdi+0x10],1 / jne 41DBCD
    41DBB9  test r12,r12 / je 41DF4A
    41DBC2  cmp eax,0x4F0 / ja 41DF4A         ; MAX WRITE SIZE = 1264 BYTES
    41DBCD  cmp [rdi+0x20],6 / jne 41DF4A     ; connection state gate
    41DBDC  lea r13,[rdi+0x250]
    41DBE3  cmp [r13],r13 / jne 41DE27        ; circular-list empty test
  accept path at 41DE27:
    41DE35  lea edx,[rbp+0x18] / call 41B7C0  ; alloc(len + 0x18) from pool
    41DE5E  call 24E8B70                      ; memcpy(node+0x18, src, len)
    41DE63..41DE7A                            ; tail insert onto conn+0x250
    41DE82  lock xadd [rdi+0x380], 1          ; queued node count
    41DE8D  lock xadd [rdi+0x390], len        ; queued bytes
    41DE9B/41DEA9                             ; lifetime totals +0x430/+0x448
    41DED7/41DEEC                             ; backpressure vs +0x384/+0x388
  No computed call, no vtable dispatch, no handler invocation anywhere.

0x41CF41 - THE DRAINER
    41CF46  lea r15,[rdi+0x250] / cmp [r15],r15
    41CF90  mov rsi,[r15]                     ; first node
    41CFA1  eax = [rsi-4] - [rsi-8]           ; len - cursor = remaining
    41CFA7  cmp eax,0x400 / cmovb ebp,eax     ; chunk = min(remaining, 1024)
    41CFBF  mov rcx,[rdi+0x18]                ; socket object
    41CFD9  call 2378CF0                      ; <-- send()
    41CFEA  lock xadd [rdi+0x428], sent       ; lifetime bytes sent
    41D057..41D07B                            ; unlink node
    41D07E/41D08C                             ; decrement count and bytes

  NODE LAYOUT: +0x00 cursor, +0x04 length, +0x08/+0x10 links, +0x18 data.
  CONNECTION LAYOUT: +0x10 type, +0x18 socket, +0x20 state, +0x250 TX queue
  head, +0x260 node pool, +0x380 count, +0x384 count cap, +0x388 byte cap,
  +0x390 queued bytes, +0x428 lifetime sent, +0x430/+0x448 lifetime totals.

  conn+0x20 == 6 is a TRANSPORT connection state, a different field from the
  session state at session+0x70.

THE LOBBY PROTOCOL - family 0x11D82194, EXACTLY FOUR MESSAGES
    msg 1  repeated u32 @0x78 (element size 4)
    msg 2  STRUCT(0x10) @0x78 + STRUCT(0x40) @0x88
           the second field's sub-table IS the ProtocolDescriptor
    msg 3  NO FIELDS (empty body)
    msg 4  NO FIELDS (empty body)
  m_messageMax = 5 is exclusive; the registration table at RVA 0x2CF0060 has
  exactly four entries keyed (message << 32) | 0x11D82194 for messages 1-4.
  Registration entry layout (0x20 bytes): +0x00 name ptr, +0x08 protocol ptr,
  +0x10 items ptr, +0x18 the packed key.

★ THE COMPLETE SERVER->CLIENT SURFACE AT STATE 6
  Tested across four independent harnesses (as the ack, as an immediate
  follow-up, as a poll response, and injected mid-stream after keepalives):
      TOLERATED (client survives to its 5s timeout):
          0x0003   keepalive; holds the socket indefinitely (44+ polls)
          0x0102   accepted as the ack. BODY IS NEVER PARSED - empty, 0x40
                   of garbage, wrong length, and a correct 0x50-byte
                   descriptor all behave identically
          0x0103   accepted; also holds the socket indefinitely
      LETHAL (instant teardown, 0 polls):
          EVERYTHING ELSE, in every position, with every body.
          Specifically ruled out: 0x0000, 0x0001, 0x0002, 0x0101, 0x0104,
          0x0105, 0x0106, 0x0107, 0x0108, 0x010A, 0x010C, 0x0200, 0x0201,
          0x0300-0x1000 (channel sweep at index 0), and a second 0x0102.
  ★ A DUPLICATE 0x0102 KILLS THE CONNECTION. Many earlier "body rejected"
    results were actually this: the harness sent a bare ack AND a second
    0x0102, and the duplicate was the cause, not the payload.

  Messages 1 and 4 were tested AS THE ACK with correct-shaped bodies
  (u32 zero/one/0xFFFFFFFF/family, and bare/empty for msg 4). All zero

    - MinHook inline hooking of internal functions.
    - The specific fix (missing CASC keys), per Section 6.

##  SECTION 7C: MEMORY-SCAN FALSE POSITIVES - READ BEFORE SCANNING  ★ rev 19
################################################################################

Four consecutive scanning approaches produced confident-looking false
positives in one session. This binary is unusually hostile to value-based
heuristics because several large regions are DENSE in exactly the constants
we search for.

  v129  "3 heap pointers + a known CRC at +0x20"      -> telemetry text
  v130  "{ptr,count} + BFS + >=3 known CRCs"          -> same region
  v131  same, aligned dump                            -> per-protocol latency
                                                         log ("+ 647 ms",
                                                         "127.0.0.1"), 0x30
                                                         stride
  v133-135 "BST walk + strictly increasing known CRCs" -> a SORTED ARRAY of
                                                         protocol CRCs next to
                                                         audio device strings
  The sortedness check does not discriminate: a sorted CRC array satisfies it
  trivially. 86 of 87 "map entries" failed self-validation once we required
  the pointed-to object to REPORT ITS OWN KEY.

RULE: a signature keyed on VALUES finds whatever region is dense in those
values. Only two things have worked reliably on this target:
  1. exact pointer equality against a known address (v136, pool instances)
  2. self-validation - make the data confirm itself (follow the pointer, read
     the object's own crc getter, require it to equal the key you matched on)
Always include (2) even when (1) looks conclusive.

The non-tournament (Battle.net) route was pursued because tournament mode is

  127.0.0.1:3724. This is a Battle.net RPC emulator. The key insight it
  proves: the client's lobby session keys (k0-k3, the schedule in Section 1)
  are DELIVERED by the bnet response GameUtilities.ProcessClientRequest, as
  attributes literally named k0/k1/k2/k3 plus cid and hostv4. We choose them,
  so zero keys means the EXISTING ZERO_KEY lobbyserv works while the client
  takes the RETAIL code path instead of --tank_TournamentMode.
  Also present: webauth.py (HTTPS :443, mirrors login-server's webserver.go
  login form), makecert.sh, run_all.bat.
  The bnet cert to use is cainj/bnet_server.pem + .key (CN=*.battle.net, SANs
  cover us.actual.battle.net, bnet-emu.fish, 127.0.0.1) - it is signed by the
  CA cainj injects, so the chain is intact.

★ THE WALL: the client connects to 1119, sends a full modern ClientHello
  (TLS 1.0-1.3, 31 cipher suites, X25519), then CLOSES THE CONNECTION DURING
  THE HANDSHAKE, at the point it validates the server certificate. The Go
  server (instrumented in bnetgo3) logs:
      === CLIENT HELLO ===  SNI:""  versions:[772 771 770 769] ...
      *** TLS HANDSHAKE FAILED: EOF ***
  This is IDENTICAL with the original bink2w64 (no cainj/owobs), so it is the
  client's own behaviour, not our DLLs.

  SNI IS EMPTY. The client connected by IP (127.0.0.1 via the hosts file) and
  sent no server name. So hostname validation is not what fails - there is no
  name to check.

★ IT IS BORINGSSL PUBLIC-KEY PINNING. The binary contains, as stripped
  BoringSSL error strings:
      "SSL public key does not match pinned public key"   @ RVA 0x298360d
      "ssl_public_key_pinning_check_failed"               @ RVA 0x298e537
      "ssl_cert_chain_bundle_verification_failed"         @ RVA 0x298e559
      "ssl_cert_chain_system_verification_failed"         @ RVA 0x298e583
      "Issuer check against peer certificate failed"      @ RVA 0x2983385
  The pinning hook is BoringSSL SSL_CTX_set_custom_verify(ctx, mode, cb),
  where cb returns enum ssl_verify_result_t { ok=0, invalid=1, retry=2 }.
  The client pins the server's PUBLIC KEY (compares it to a hardcoded pin),
  which is why NO cert/CA/verify_mode change can pass it - cainj does CA-add
  + verify_mode=0, both irrelevant to a public-key pin. This is exactly what
  Sidiusz described: he did NOT add a CA, he "patched the heap-parsed pin/
  verify result", hooking the high-level pinning + chain-verify and forcing
  them to pass, "one shot at load is enough".

★ REFINEMENT (rev 20, from cainj's own diagnostic): the pin is NOT a naked
  BoringSSL app_verify_callback in the SSL_CTX. cainj's BFS from the cert
  store logged: "NO object within depth<=2 holds cert_store==store => pin is
  likely a C++ WRAPPER VIRTUAL METHOD, not an OpenSSL app_verify_callback."
  So the Blizzard networking layer (bnl) wraps BoringSSL and the pin check is
  a VIRTUAL METHOD on that wrapper object, reached through its vtable - which
  is also why the BoringSSL pin strings have no static xrefs. cainj already
  finds this wrapper (it logs "WRAPPER <addr> verify_mode +0x94" and knows
  its vtable g_wrapVtbl). The BoringSSL custom_verify callback most likely
  just forwards into this wrapper.
  => The target is a VTABLE SLOT on the bnl TLS wrapper, and the patch is to
     force THAT method's returned verdict (Sidiusz's "heap-parsed pin/verify
     result"). Next concrete step: dump g_wrapVtbl's slots (extend cainj to
     log them, or read the wrapper vtable live with owobs), disassemble each
     to find the one returning the verify enum, and patch its result.

★ THE FIX (a DATA write, so Arxan-compatible), TWO OPTIONS:
  (a) repoint the custom_verify callback in each live SSL_CTX to a stub that
      returns 0 (ssl_verify_ok). cainj already locates SSL_CTX objects (it
      writes verify_mode at ctx+0x80 / +0x94), so the callback pointer is a
      nearby field to read and overwrite.
  (b) find the pinned public-key blob on the heap and overwrite it with the
      SHA-256 of OUR cert's public key, so the compare passes legitimately.
      cainj found the cert store adjacent, so the pin set is likely near it.

★ WHY IT ISN'T DONE YET: the callback/pin ADDRESS is not recoverable from
  the static dump. Every BoringSSL error string has ZERO lea/pointer xrefs -
  the whole error subsystem is behind the same obfuscation as the JAM
  strings (Section 7B). Shape-based static search for the callback returns
  ~375 small return-0/1 functions, too generic to isolate. So the address
  needs RUNTIME discovery: an owobs pass over the SSL_CTX objects cainj
  finds, reading the custom_verify callback field and either repointing it or
  following it to the pin blob.

★ HIGHEST-LEVERAGE INPUT: Sidiusz has the exact function/offset he patched
  and reached the login form + "CONNECTING TO GAME SERVER". One question -
  which function, what offset - likely saves the entire runtime hunt. He is
  responsive and has moved off OW1 (no reason to withhold). He also confirmed
  the handshake field-for-field and that lobby crypto is a nonce swap, not

  If the bnet path completes, the client should follow the RETAIL sequence

   Untried angles: reconstructing a pool instance from a known vtable and
   calling allocate_pool (slot 6); locating the switch by its jump table
   (needs tighter constraints than "dwords in .text range" - try requiring the
   targets to lie within one .pdata function).

4. RECOVER THE WIRE ENCODING.
   The schemas give field types and order; the serialisation is unknown and
   is NOT a flat struct dump. Without it no constructed body can be correct.
   The per-field +0x20 pointers are vector-resize thunks, not codecs, so the
   encoder is generic and lives in the decode/dispatch path.

5. OverwatchGM.exe / --tank_tournamentmodeadmin.
   A separate binary implementing the same protocol, possibly with different
   Arxan coverage. Check whether your install has it. Completely untested.

6. THE 292-BYTE BLOB TRAILER.
   We send 36 zeros; the real one carries structure. Sidiusz confirms zeros
   reach state 6, so this is not the wall, but it is the one place we
   knowingly send something a real server never would.

7. LOOTBOXES. Not started. Downstream of everything above.
